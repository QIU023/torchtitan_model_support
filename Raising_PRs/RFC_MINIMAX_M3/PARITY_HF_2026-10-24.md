# MiniMax M3 与 HF 的数值对齐（2026-10-24，8×A4000 sm86）

脚本：`torchtitan/scripts/checkpoint_conversion/numerical_tests_minimax_m3.py`（分支 `minimax_m3`，worktree `/workspace/wt_m3`）。
做法照搬 K3 的 `numerical_tests_kimi_k3.py`：不加载发布的权重，把发布的 HF config（`MiniMaxAI/MiniMax-M3` @ `f0e1c1e04d40177e4673a22097036854f536e9c0`，只下 json / tokenizer）缩小到 titan 的 `debugmodel`，titan 随机初始化，`MiniMaxM3StateDictAdapter.to_hf` 导出，存成 safetensors 后用 HF 的 `from_pretrained` 走它自己的 checkpoint conversion 加载（missing / unexpected / mismatched 全空才继续）。同一条图文 prompt（336×336 图，333 token，144 个图像 token），两边各做各的预处理。debug 的选块预算是 4×16=64 token，所以 333 token 的序列在稀疏层确实只看部分块。

脚本选项：`--dtype {bfloat16,float32}`、`--attn_backend {varlen,flex}`（只管 full attention 层，稀疏层永远 flex；fp32 + varlen 会被拒绝，因为 varlen 内部转 bf16）、`--experts_implementation {grouped_mm,eager}`（HF 侧）、`--force-hf-blocks`、`--force-hf-routing`。

## 定位链（fp32 下逐个算子拆，探针在 `hf_parity_probes/`）

1. **titan 选块 = 参考实现，100%**（`diag_blocks.py`）：用 titan 的 index q/k 按 HF 语义（fp32 点积、因果 mask、块内 max-pool、本块 +inf、topk）重算，每层都和 titan 一致；偏离参考的是 HF，第 1 层只差 0.075%，往后累积。
2. **indexer 本身一致**（`diag_indexer.py`）：同一份输入，HF indexer 与 titan indexer 的 q/k 相对差 1.2e-7（投影、Gemma norm、部分 RoPE 都对）。
3. **差异从图像 token 进入**（`diag_hidden.py`）：图像之前的 text token 第 0 层 attention 输出差 5e-8，图像 token 及其后约 2e-5。
4. **HF 的 Conv3d patch embedding 在 fp32 下跑 TF32**（`diag_vision.py`）：PyTorch 默认 `cudnn.allow_tf32=True`。对 HF fp64：HF fp32 开 TF32 3.3e-4，关 TF32 6.8e-7；titan fp32（patch embedding 是 Linear）4.0e-7。脚本已设 `torch.backends.cudnn.allow_tf32 = False`。
5. **titan 的 varlen 在 fp32 下其实是 bf16**：`VarlenInnerAttention.forward` 把非 fp16/bf16 输入转成 bf16（`attention.py` 的 `attn_dtype = torch.bfloat16`），所以 fp32 对比必须 `--attn_backend flex`。flex fp32 对 fp64 参考 2.35e-7（`diag_attn0.py`）。
6. **剩下的 fp32 差距全部是 titan routed experts 的 bf16 grouped GEMM**（`diag_moe.py`）：路由 ids 与权重逐位相同，shared expert 1.1e-7；routed 部分 6.0e-3。用 titan 自己的参数和 ClampedSwiGLU 在 fp32 重算 routed 部分，对 HF fp32 是 1.4e-7（语义完全一致）；titan 实际输出对它自己的 fp32 算法是 6.0e-3，原因是 `RoutedExperts.forward` 的 `routed_input_RD.bfloat16()` 和 `GroupedLinear._grouped_mm` 的 `weight.bfloat16()`。这是 titan 所有 MoE 的设计，不是 M3 的问题。
7. 强制选块后，fp32 逐算子：attn0 5.4e-7、ffn0（dense，addcmul）1.5e-6、attn1（MSA）5.0e-7、ffn1（MoE）4.9e-3，后者即第 6 点。

结论：除 HF 的 TF32 卷积（脚本已关）和 titan 的 bf16 grouped GEMM（设计如此）外，每个模块在 fp32 舍入级别和 HF 一致。bf16 下的选块翻转是近似平局（被选第 k 块与第 k+1 块的分数差中位数约 1e-2，分数本身约 10）在 bf16 噪声下翻转；强制 HF 选块后全位置 KL 4.1e-5。

## 另一个发现：flex backward autotune 绑错捕获张量的顺序（PyTorch inductor bug）

- 现象：M3 debug 在 2 卡 FSDP 上编译 MSA 层的 flex backward 时 `CUDA error: an illegal memory access`；`CUDA_LAUNCH_BLOCKING=1` 下不复现，单卡也不复现。
- 定位：`compute-sanitizer --tool memcheck`（`PYTORCH_NO_CUDA_MEMORY_CACHING=1`）抓到 `triton_flex_attention_backward` 读 int64 越界，正好在 2048 元素的 `block_T` 之后。打点（`flex_bwd_capture_order/spy.py`）显示 backward autotune 给 benchmark 的捕获张量顺序是 HOP 顺序 `[(2048,), (2048, 2, 4)]`，而 kernel 签名按首次使用排成 `[(2048, 2, 4), (2048,)]`。真实调用绑定正确（梯度对 SDPA 1e-6）。
- 根因：`torch/_inductor/kernel/flex/flex_attention.py` 的 forward lowering 已经用 `list(choices[0].input_nodes)` 做 autotune 输入（注释 "Use generated inputs because codegen can inline capture producers."），backward lowering 仍用 `bwd_input_nodes + score_mod_other_buffers + mask_mod_other_buffers + mutated_grads`。mask_mod 捕获两个以上张量、且 HOP 顺序和 kernel 首次使用顺序不同就会错位。最小复现 `flex_bwd_capture_order/repro_flex_bwd_capture_order.py`（纯 PyTorch，`spy.py` 下可见错位；memcheck 未必报，因为越界读常落在相邻分配里）。
- 修法验证：`patch_bwd_autotune_inputs.py` 把 backward 的 autotune 输入换成 `list(choices[0].input_nodes)`，MSA 重放 memcheck 0 错误，2 卡 FSDP 不开 blocking 跑满 10 步。
- M3 侧处理：mask_mod 只捕获一个张量（每个被选块的闭区间 `[start, end]`，`[T, G, S, 2]` int32），不依赖 PyTorch 修复；代码里一行注释说明这条约束。
- 状态：issue 和修复 PR 都还没发（对外动作，等用户决定）。环境：torch 2.16.0.dev20261023+cu130。
